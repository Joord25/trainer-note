# Member home and assistant context (2026-10-10)

Member cards use the current structured training goal, with legacy member.goal only when no structured goal exists. Custom goal titles use detail. The member information editor leaves the legacy goal unchanged when a structured goal exists, and directs goal edits to the training goal dialog. The dialog header identifies the actual member rather than presenting the original onboarding route as current membership status.

`trainerDirectory` is an authenticated, App Check enforced callable. It constructs every path from the authenticated UID, validates 1–50 unique member IDs, checks ownership via the parent document, and returns only goal labels, latest record date, and saved analysis/plan availability. It does not invoke Gemini or read full record collections. Each member requires a bounded parent/goal/latest-record/latest-analysis/plan read; queries project only required fields. Batches run five members at a time. The client refreshes the selected folder on home entry and connection recovery; metadata errors are displayed, not interpreted as missing data. Saved artifact labels do not assert that analysis is up to date. Opening the member still validates the saved workflow against its input key.

The assistant fixes the member name above the conversation and shows the server-selected topic and actual record scope per answer. Existing messages can use their stored chatContext and contextScope; absent scope metadata is explicitly unknown. Nutrition uses the structured primary goal rather than the legacy goal; secondary goals are not silently promoted. Separate cases remain marked separately. New response topic metadata adds no inference calls.

Validation: member-overview emulator tests cover latest data, canonical/custom/legacy goals, empty states, isolation, and invalid IDs. Service tests cover nutrition primary-goal precedence and persisted topic. Existing chat/service tests remain the regression suite.
